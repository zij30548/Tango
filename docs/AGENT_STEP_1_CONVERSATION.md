## 做了什么，为什么需要

以前聊天记录跟着某次歌单任务刷新，聊偏好和找歌使用两条链路，消息可能互相覆盖。现在单独保存会话：**聊天负责记录交流，任务负责找歌和修改歌单。**

你可以先找歌，再说“记住我喜欢粤语 R&B”，确认保存后继续修改原歌单。偏好回复留在原会话，任务刷新不会把它删掉。大聊天区和固定底部多行输入也已接入：Enter 发送，Shift+Enter 换行；提交失败保留草稿。

这一步建立后续意图路由、多轮记忆和任务编排共同使用的会话基础。它本身没有提高模型的语义理解能力。

## 一条消息怎么走

```text
输入文字
  → 分配稳定的 messageId
  → 后台事务保存消息与接收回执
  → 客户端收到有效回执，才清空对应且未再编辑的草稿
  → 复用现有找歌任务或偏好提议能力
  → 把服务端任务回复／本机确认回执写回同一会话
```

- **conversation**：一段可以持续交流的会话。
- **turn / messageId**：本轮用户消息；找歌提交也沿用它作为幂等请求 ID。
- **task**：有独立版本、进度、暂停和预览的执行任务。聊天记录不再由任务快照替换。
- 消息提交结果不明时先查原 ID 的回执，不盲目另发一次。已接收仅表示消息保存成功，不表示模型已完成任务。
- 恢复历史只读取记录和关联任务；不会重新发送聊天、确认偏好或自动播放。继续本机查询需要用户明确操作。

## 面试怎么讲

> 我把音乐助手的会话和执行任务拆开了。用户消息先带稳定 ID 入库，确认保存后才清草稿，再交给已有音乐能力。任务回复按任务和版本合并，偏好仍要求用户确认。超时查询原回执，历史恢复不重放业务，并测试了重启、并发、账号隔离和迟到响应。

1. **为什么会话和任务分开？** 一段对话可能横跨找歌、解释和偏好；任务有自己的版本和生命周期，不能拿它的快照覆盖全部交流。
2. **超时为什么不能直接重试？** 服务端可能已提交。先查稳定 ID；明确重试继续沿用原 ID，防止重复任务和重复收费。
3. **为什么这里不用多个 Agent？** 当前问题是消息和执行状态的可靠关联，用事务、幂等和状态校验解决。专业分工以后按实际任务收益评估。
4. **聊天记录就是模型记忆吗？** 不是。保存记录解决恢复；挑选相关上下文、保留约束、偏好冲突和遗忘治理还要单独实现和评测。
