# 音乐助手演示闭环交付

2026-10-23。本步围绕“对话、找歌、修改、偏好、恢复、采用”完成可检查的演示路径。它解决已知复合请求容易整轮拒绝、聊天操作不完整，以及无法说明实际验收范围的问题。

本轮证据见 [demo-release-verification.json](agent-upgrade/demo-release-verification.json)。实际完成真实桌面演示，模型调用14次；80次授权累计61、剩19，余量不自动消耗。工程测试通过不等于上线验收，也不提供未经独立评测的总体完成率或准确率。

后续又发现并修复了记忆提议的疑问／截句授权边界，补充客户端与数据库复查；最新范围见 [后续测试交付](AGENT_DEMO_FOLLOWUP_TESTS.md)。本页和原报告保留原版本成绩。

## 本步怎样工作

```text
输入原话 → 持久保存消息 → 选择理解路径
  ├─ 明确且所有分句均被覆盖：受限需求编译
  └─ 自由表达、引用、条件或无法完整覆盖：既有模型路由／澄清
       ↓ 两条路径共用严格计划校验、权限和版本检查
  偏好提议／音乐任务／只读回复／任务控制
       ↓ 音乐任务
  规划 → 研究 → 曲库工具 → 观察与有界补查 → 编排 → 预览
       ↓ 用户明确采用
  设备核验并更新队列 → 按当前账号播放权益请求音频
```

受限需求编译把原句拆成带来源和范围的要求：长期偏好、本次场景、临时约束、时长及显式确认依赖。只有全部分句都能解释才使用这条路径；不能识别的部分不会被悄悄丢弃。它减少常见复合指令的路由格式失败和额外调用，**不替代自由表达的模型理解，也不证明复杂语义已经全部解决**。后续音乐规划仍受原任务契约约束。

- “记住我喜欢粤语，再推荐20分钟微醺歌单”：保存口味与推荐是独立要求。口味先提议，未确认不写入；取消口味不取消独立找歌。
- “记住我喜欢粤语，确认保存后再推荐20分钟微醺歌单”：明确建立确认依赖。取消提议就跳过依赖的找歌，确认后才继续。
- “只用于今晚”“不要记住”等说明属于本次任务，不能变成永久偏好。
- “时长改成40分钟，其他不变”：绑定当前任务，逐字段修改；撤回恢复上一份已保存方案。信息缺失或时长超范围时先澄清。

聊天里的确认、锁定、采用等本机操作也先保存原话，再核验当前账号和状态。查看口味只读取当前账号本机已确认的值，不调用模型，不把聊天推测当成已保存记忆。路由、模型尝试和任务进度留有持久记录；模型或曲库文本不能授予执行权限。

真实桌面演示走通：6首约20分钟→锁定前三首→11首约40分钟→撤回原6首→暂停、退出Qt、重开继续→采用播放。前三首ID和顺序保留，重复采用保持同一回执，播放进度没有重置。另验《十年》4个版本、会话歌手历史、引用“取消任务”不执行、邓紫棋先澄清身份再查发行、原跑步请求返回12首，以及取消爵士提议后仍保留粤语口味。新作结果来自曲库日期与归属；没有验证平台发行完整性。观察到播放进度不等于验证整首或会员完整播放。

首次新增测试 helper 在填写输入前检查发送按钮，导致测试未发出请求；已修复 helper 并保留初次失败日志。没有删断言或重跑挑选真实模型最好结果。原生最终独立运行 17.778 秒，适用本机 macOS／Qt5，不能外推为线上延迟。

仍需分开看待的限制：

- 风格调整依据曲库来源、文字与元数据约束；没有听音分析，不能保证主观听感、节奏或人声比例。
- 20／40分钟是编排目标；真实曲库不足时应展示缺口，不能用模拟曲目的精确时长承诺真实请求必然满足。
- 恢复的是**已创建并持久保存的音乐任务与会话**。未确认偏好提案仍在 Qt 内存中，不承诺跨重启恢复；重开后应重新提出并确认。
- 真实模型语义稳定性、独立新题总体成绩、推荐听感与会员完整播放，均不能由本页工程测试代替。旧失败、旧源码哈希和旧成绩保持原范围。

## 五分钟聊天演示

准备：按 [运行说明](../README.md)打开当前 App，后台模型已由开发者配置。播放前使用演示者自己的网易云授权；先确认网络可用。以下是操作顺序，网络或模型等待不承诺固定五分钟内结束。

| 顺序 | 在输入框发送／操作 | 应观察什么 |
| --- | --- | --- |
| 1 | `记住我喜欢粤语，再推荐20分钟微醺歌单` | 出现待确认口味和独立找歌进度；最终是歌单预览，尚未播放 |
| 2 | `确认保存口味` | 明确回复已确认保存；这次确认只授权当前提议 |
| 3 | `查看我的口味` | 返回当前账号在本机已确认的口味，临时场景不应被保存 |
| 4 | 等预览完成，发送 `保留前三首` | 当前预览前三首被锁定；聊天确认已保留 |
| 5 | `时长改成40分钟，其他不变` | 同一任务产生新预览，目标改为40分钟；前三首及其他已确认条件保留 |
| 6 | `解释当前歌单` | 基于当前候选、来源和约束说明依据，并说明未分析音频 |
| 7 | `撤回修改` | 返回修改前的20分钟方案；不自动播放 |
| 8 | `暂停任务` | 任务变为暂停；这是暂停音乐研究任务，不能误讲成播放器暂停 |
| 9 | 正常退出 App，再按同一入口打开；进入音乐助手，发送 `继续任务` | 恢复同一任务、会话及已确认口味；已完成预览不会重新研究或自动播放 |
| 10 | `采用歌单` | 明确采用后才更新队列并尝试播放；无权限或试听按上游实际结果处理 |

可选依赖分支：另开新对话，发送 `记住我喜欢粤语，确认保存后再推荐20分钟微醺歌单`，再发 `取消口味`。应该取消提议并跳过依赖找歌。不要在主线未确认提议时退出 App，然后声称该 RAM 提议已经恢复。

真实曲库失败或无法播放时，展示具体失败并停止该分支；不要把旧歌单当成本轮成功，也不要在演示中自动反复调用模型。

## 面试怎样讲

可放入简历的表述：

- 基于 C++／Qt、Python FastAPI 与 LangGraph 实现对话式音乐助手，支持场景找歌、发行查询、连续修改、确认式偏好及任务恢复。
- 设计规则／模型混合路由与类型化能力计划，校验指令来源、动作依赖和任务版本；通过 MySQL 业务检查点、CAS／租约、调用前额度预留及幂等回执控制重复和迟到操作。
- 建立离线契约、隔离数据库、原生桌面及真实模型／曲库分层验证，保留失败、调用预算和版本证据；推荐质量与工程通过率分开衡量。

**30 秒概括：**我为音乐助手做了规则与模型结合的受控路由。能完整解释的常见复合需求先拆分长期偏好、本次约束和确认依赖，再编译为能力计划；自由表达由模型提案，两条路径共用权限、版本和预算校验。音乐任务由固定 LangGraph 图执行，持久保存进度，预览、采用和播放分开。我用真实 Qt 和隔离 Python 后台验证修改、确认、恢复与幂等，工程结果和真实推荐质量分别记录。

1. **为什么不全交给模型？** 明确请求可减少路由格式失败和额外调用；受限编译只处理完整覆盖的范围，不用规则冒充开放语义理解。
2. **怎样防止漏掉要求或误写记忆？** 保留分句来源和范围；有未解释内容就退出编译路径。偏好提议与实际写入分开，只有当前明确确认才保存。
3. **恢复是否会重复执行或计费？** 读取持久任务不会自动重发未知付费请求，恢复仍受账号、版本、租约和预算约束；已完成预览直接恢复。未确认的本机偏好提议不在持久任务恢复承诺内。
4. **这是多 Agent 吗，测试准确率多少？** 当前是固定研究图及受控角色，不是动态多 Agent。本轮原生 3／3 是模拟上游的业务闭环测试，不能作为真实模型总体准确率；真实语义、曲库和听感须另设题集与分母。

下一步按本轮真实失败与最终证据决定优先级，再推进 MCP、动态调度与质量监测；这些尚未完成的能力不写进已实现的简历描述。
