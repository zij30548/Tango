# 待确认动作的持久化与恢复

更新：2026-10-24。本阶段补齐探歌音乐助手的本机确认与后续动作续接，不改变现有固定 LangGraph，不增加 Agent 角色。工程验收采用临时数据库和模拟上游，结果与边界见下文。

后续[新题修复阶段](AGENT_E2E_REPAIR.md)另扩展了采用请求的原ID持久化和后台原动作/版本事实。下文原阶段测试数字保留当时范围，不改写成新采用恢复或模型效果的成绩。

## 这一步做什么

以前，用户说“记住我喜欢爵士，然后按这个口味找歌”，未确认提议和后续动作主要在 Qt 内存中。关闭窗口或重启后，这些内容可能丢失；确认已保存、请求是否提交，也缺少统一的本机续接记录。

现在先把动作写入当前账号的本机 SQLite，再显示提议或派发。恢复时先核对后台原路由，再分别处理未确认、已确认未发出和已发出但结果未知三种情况。**恢复可以找回状态，不能替用户确认，也不能凭超时重发付费请求。**

## 请求与恢复怎样走

```text
当前消息 → 后台产生并保存类型化路由 → Qt 校验路由
  → 本机 journal 保存计划、偏好基线与动作状态
  → 展示待确认提议／按依赖执行获准动作

重开会话 → 读取当前账号、设备、会话的本机 journal
  → GET 后台原路由，重新校验并对照计划
  ├─ 未确认：重新显示提议，等待用户明确确认或取消
  ├─ 已确认、剩余步骤未发出：提示“继续未完成步骤”，等待新指令
  └─ 已发出、回执未知：按原 requestId 只读查询后台，不重发 POST
```

确认偏好时，程序在同一个 SQLite 事务中检查基线版本与摘要，然后更新偏好、条目、版本、动作状态和固定回复回执。任何一项失败，整笔回滚。重复同一确认返回原回执，不再增加偏好版本；更改决定或换成其他内容不能冒用旧确认。

版本检查还能防止“旧值 A → 改成 B → 又改回 A”后，旧提议覆盖用户的新决定。只比较文字无法发现这类变化。

后台回执的 `recorded` 只说明原请求有持久记录，任务此后可能失败、取消或更新，仍要读取任务状态。查不到记录返回 `unknown`，也不能据此认定请求没有执行。旧请求的核对使用独立上下文，不抢占较新的任务、租约工具或订阅。

确认回复按照稳定事件 ID 重送，后台幂等去重。重送这类回复不会调用模型或播放音乐。

## 技术栈与代码

采用 C++17／Qt5、Qt SQL／SQLite，以及现有 Python FastAPI／MySQL。SQLite 保存设备上的确认与派发记录；MySQL 继续决定后台路由、任务、请求回执和额度事实。没有增加 Redis 锁或第二套任务运行时。

| 源码 | 本阶段作用 |
| --- | --- |
| [radiostore.h](../radiostore.h)、[radiostore.cpp](../radiostore.cpp) | `preferenceSnapshot`、`journalRoute`、`routes`、动作 CAS、确认锚点和原子 `decidePreference` |
| [mainwindowradio.cpp](../mainwindowradio.cpp) | 先落盘再派发、恢复提议、明确续接、稳定回复和旧请求观察 |
| [conversationclient.cpp](../conversationclient.cpp) | `restoreRoute` 只 GET 原路由，重新核验消息与计划，不重新请求模型路由 |
| [musictaskclient.cpp](../musictaskclient.cpp) | `observeRequest` 查询原请求；旧操作观察不切换当前任务 |

| [app.py](../backend_py/tango_backend/app.py)、[task_store.py](../backend_py/tango_backend/task_store.py) | `GET /v1/tasks/requests/{deviceId}/{requestId}`，按账号与设备只读关联持久请求和任务 |

日志按 `profile + deviceId + conversationId + turnId` 隔离，动作再按 `actionId` 区分。单条路由最多 4 个白名单动作，同一账号／设备／会话最多接纳 32 条有效活跃路由，每次最多读取 32 条用于恢复；计划与结构有大小边界。相同消息的计划和偏好基线不可被重复回执覆盖。

## 自己怎样检查

1. 在同一账号的同一设备里提出“记住我喜欢爵士，然后按这个口味找歌”，等提议显示后关闭软件，再重新打开原会话。应重新显示提议，口味仍未写入，也不应自动执行依赖该确认的找歌。
2. 核对提议，输入“确认保存口味”或“取消口味”。取消后依赖此确认的步骤不执行；确认后只有本轮仍有效、任务版本匹配的步骤可以继续。也可使用已有的确认操作修改提议后保存。
3. 如果恢复提示尚有未派发步骤，输入“继续未完成步骤”。输入“核对未完成步骤”只核对原请求，不授权新的派发。已经切换话题的旧步骤需要重新提出。
4. 发生发送超时后重开会话，应查询原请求。查不到时保持未知，不应自动产生另一条提交。可结合[诊断命令](AGENT_DIAGNOSTICS.md)检查原请求与任务，结合 [LangSmith](LANGSMITH_TRACING.md)观察已采集的后台过程。
5. 换账号、换设备或开启其他会话，不应出现之前的待确认提议。提议产生后手工修改长期口味，再确认旧提议，应拒绝覆盖。

这些步骤是人工检查指引，不等于以上所有故障窗口已经人工复现。日常使用真实模型与真实曲库的结果，也应与下面的隔离工程验收分别记录。

## 范围与边界

- 有效期为 7 天。过期后不恢复、不允许确认；过期记录保留拒绝重放的事实，不能把失效称为历史内容已物理删除。
- 恢复只处理当前设备、账号和会话中的记录，原消息还需要出现在当前已加载的会话窗口。它不提供跨设备迁移，也不恢复所有历史消息中的旧提议。
- 计划不一致、存储损坏、版本变化或后台核验失败时停止。模型文字、本机日志和设备提交都不能授予后台权限。
- 偏好保留在账号本机空间，不因本步上传已有偏好。凭据、Cookie、密钥和播放地址不能写入这份动作日志。
- `dispatched` 在恢复时变为 `unknown`。本阶段没有持久化可安全重放的完整网络请求，因此未知操作仅观察，不能补发；未知单曲查询或播放也不会在恢复时自动执行。
- 清空播放队列的短效确认、采用歌单与播放继续使用原有明确确认机制，本步不承诺扩展它们的恢复范围。
- 偏好历史派生删除、独立真实效果评测、线上反馈告警仍是后续工作，本阶段没有完成整个运营闭环。

## 面试怎样讲

**30–60 秒概括：** 我为音乐 Agent 增加了待确认动作的持久恢复。后台 MySQL 保存路由和任务的权威状态，客户端 SQLite 保存账号、设备、会话隔离的动作日志。确认偏好采用版本 CAS，把偏好、条目、动作完成状态和回复回执放进同一事务，防止重复确认和旧提议覆盖新决定。重启后先查询后台原路由；未确认提议重新等待用户，已发出但结果未知的请求只按原 ID 查询，不自动重发。验收用临时数据库、模拟服务和失败注入，真实推荐质量另外评测。

1. **为什么不把这些内容都放在聊天历史里？** 聊天是表达，动作需要明确的状态、确认来源、依赖、版本和幂等标识；单靠文本无法安全判断是否已执行。
2. **怎么保证不重复执行？** 本机确认写入用事务与 CAS，回复用稳定事件 ID；网络提交结果未知时只观察后台事实。不能声称跨客户端与网络天然具备全局“恰好一次”。
3. **为什么已经有 MySQL，还要用 SQLite？** 后台任务和额度继续由 MySQL 管理，长期口味与本机确认记录遵循设备侧的数据边界。恢复必须核验后台计划，两者各管自己的状态，不把客户端日志当后台执行证据。

下一步按既定顺序冻结独立真实任务题集与评分标准，分别评估任务完成、路由、约束、推荐相关性、恢复、耗时和成本；新增付费测评仍需要明确预算。
