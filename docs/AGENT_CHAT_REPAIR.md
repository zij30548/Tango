# 聊天界面与实际失败修复

2026-10-23。本步先解决用户实际遇到的不可用问题，再继续 MCP；没有新增多 Agent 角色，也不把界面简化当成模型能力提升。

## 做了什么

助手页面只保留聊天区、输入框和发送。顶部曲库搜索、添加音乐、任务面板、额度、偏好面板、歌手下拉和结果表不再占用聊天页面；播放器和侧栏仍属于音乐软件外壳。选择歌手、采用歌单、播放某首、确认口味改成聊天输入。

| 原问题 | 现在的处理 |
| --- | --- |
| 跑步推荐无法形成方案 | 明确的场景推荐直接进入新音乐任务，避免误继承上一轮歌手发行需求；复杂修改仍走受控模型路由 |
| 查新歌却混入其他歌手的热门歌单 | 纯发行任务只走发行查询；未确认歌手身份时停止编排。唯一精确姓名或上游别名可以继续，同名冲突仍追问 |
| 问之前哪些歌手却解释歌单 | 单独读取本账号、本设备、本会话最近 200 条已路由消息；回答明确范围，不声称记得全部历史 |
| 搜索／播放指定歌曲失败 | 新增 `music.lookup`；用真实曲库查歌，不要求先生成研究歌单。搜索不自动播放；明确要求播放且歌名、歌手唯一精确匹配才请求播放 |
| 删除全部歌曲含义不清 | 先澄清范围。当前支持明确确认后清空待播放队列，保留收藏、历史与磁盘文件；队列变化、切账号或跨话题会使确认失效 |
| 发送后一直像在等待 | 搜索成功、失败、空结果与旧请求失效都会结束“正在查找”提示，不把失败显示为成功 |

同名歌曲展示专辑与时长。多版本时输入“播放第1首”等进行选择；生成歌单后输入“采用歌单”；歌手歧义时输入“选择歌手 1”；口味提议使用“确认保存口味”或“取消口味”。临时场景不会自动写入长期偏好。

## 请求怎样走

```text
输入原话 → 后台持久保存消息
  → 当前本机上下文中的明确确认／选择：核验状态后执行
  → 其他请求：确定性窄规则或一次模型路由 → 严格契约校验
      → 单曲查找：Qt → 本机网易云适配 → 候选 → 用户选曲／核验后播放
      → 场景／发行：LangGraph → 曲库工具 → 校验 → 歌单预览 → 明确采用
      → 历史问题：只读所属会话 → 程序生成回答
```

本机操作也先保存原话，重启读取历史不会再次播放、确认或删除。紧接偏好提议的明确确认允许继续原复合请求的依赖步骤，跨话题不能唤醒旧找歌。播放地址和会员权益仍按网易云当前账号返回核验。

技术栈沿用 C++17／Qt5、Python／FastAPI／LangGraph、MySQL／Redis 和 Node 网易云适配。确定性规则处理明确且边界窄的操作，模型处理开放表述；规则不是推荐听感或复杂意图准确率的证明。

## 局限与下一步

这一步修复了用户列出的处理路径，不能宣称所有复杂表达可靠。复合记忆的拒绝仍须通过可复现提案定位；已细分安全原因码，日志只记录关联 ID 和固定原因，不记录密钥、Cookie 或整段聊天。总体任务完成率、总体语义准确率、推荐听感仍未知。

下一步先处理该拒绝的不稳定性并增加独立表达，之后再进入 MCP。历史旧错误回复保留原记录，不会被本步静默改写成成功；如要重新测试，输入“新对话”即可，原历史仍保留。

## 面试怎样讲

我把音乐助手从一组功能面板改成统一对话入口，并针对真实失败补齐了单曲查找、会话历史与发行隔离。请求先持久化，模型只提出受控动作；程序决定权限、版本和是否执行。验证分为工程回归、真实模型加固定曲库、实际桌面操作，保留一次复合记忆失败，不把模拟通过率当总体准确率。

- 为什么有规则还需要模型？明确操作用规则减少调用与不确定性，复杂表达用模型；两条路径执行相同校验。
- 怎么避免搜歌变成播放？搜索与播放有独立参数与当前原话授权，设备还核对唯一精确曲库匹配。
- 怎样保证简化界面后确认仍可靠？确认原话先入库，再绑定账号、当前提议和版本；历史读取不授权执行。
- 测试全部通过就能上线吗？工程守卫通过与模型稳定、真实曲库和会员播放是不同验收范围，当前仍有明确缺口。
